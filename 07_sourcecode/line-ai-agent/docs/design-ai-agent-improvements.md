# ออกแบบฟีเจอร์ปรับปรุง Greenman AI Agent

เอกสารนี้วิเคราะห์และออกแบบ 3 ฟีเจอร์ที่เสนอไว้ ก่อนเริ่มพัฒนาโค้ดจริง เพื่อให้ทุกฝ่าย (คือคุณ 😄) เห็นภาพ requirement, flow, data model และจุดที่ต้องตัดสินใจ ก่อนลงมือ

สถานะปัจจุบันของระบบ (baseline):
- `app/services/gemini_service.py` เรียก Gemini แบบไม่มี "ความจำ" เลย — ทุกข้อความคือการเริ่มบทสนทนาใหม่
- `run_klive_command` สามารถเรียก `k-delete` / `k-update` ผ่าน Gemini ได้ทันทีโดยไม่มีการยืนยันจากผู้ใช้
- Firestore ปัจจุบันมี `bot_users` collection (1 doc ต่อ user, เก็บ status + current_mode), `notes`, `reminders`
- มี `/cron/check-reminders` endpoint และ external cron (cron-job.org) ที่ยิงทุก 1-5 นาทีอยู่แล้ว — ใช้ต่อยอดได้

## ฟีเจอร์ที่ 1: ความจำบทสนทนา (Conversation Memory)

### ปัญหา
ผู้ใช้ถามต่อเนื่อง เช่น "งานนั้นกำหนดส่งเมื่อไหร่" หลังจากถามชื่องานไปแล้ว บอทจะไม่รู้ว่า "งานนั้น" คืออันไหน เพราะแต่ละข้อความถูกส่งเข้า Gemini แบบเดี่ยวๆ

### เป้าหมาย
- บอทจำบริบท 5-10 ข้อความล่าสุดต่อผู้ใช้ได้ ใช้ตอบคำถามต่อเนื่อง/สรรพนามอ้างอิงได้ถูก
- ความจำต้องอยู่รอดแม้ Render restart/sleep (เก็บใน Firestore ไม่ใช่ memory เฉยๆ)
- มีกลไกเคลียร์ความจำ (คำสั่งเอง + หมดอายุอัตโนมัติ)

### ขอบเขต (Scope)
ใช้กับโหมด "task" และ "chat" เท่านั้น (โหมด note/remind ไม่ผ่าน Gemini chat อยู่แล้ว ใช้ command parsing ตรงๆ)

### Data model
เก็บใน Firestore doc เดิม (`bot_users/{user_id}`) เพิ่ม field:
```
conversation_history: [
  {"role": "user", "text": "...", "ts": "2026-07-14T10:00:00+07:00"},
  {"role": "model", "text": "...", "ts": "..."},
]
conversation_updated_at: "2026-07-14T10:00:00+07:00"
```
เหตุผลที่เก็บเป็น field เดียวใน doc เดิม (ไม่แยก collection ใหม่): หลีกเลี่ยงการทำ Firestore query แบบ composite (`.where().order_by()`) ที่ตอนนี้ยังมีปัญหา 403 อยู่ — การอ่าน/เขียน doc เดี่ยวด้วย `.get()`/`.set()` เป็น operation ที่ง่ายและเชื่อถือได้กว่า

### กติกาการเก็บ/เคลียร์
- เก็บแค่ "ข้อความสุดท้ายที่ผู้ใช้เห็นจริง" ไม่เก็บ intermediate tool-call step (ของ forced-tool-turn 2 รอบ) — กันบทสนทนาโป่งและกัน token cost
- เก็บสูงสุด 10 คู่ (20 ข้อความ) ตัดของเก่าสุดทิ้งเมื่อเกิน
- Auto-reset ถ้าข้อความล่าสุดห่างจากตอนนี้เกิน 3 ชั่วโมง (กันบริบทเก่าข้ามวันมาปนกับเรื่องใหม่)
- คำสั่งแมนนวล: พิมพ์ "เริ่มคุยใหม่" หรือ "ลืมที่คุยไป" → เคลียร์ history ทันที
- ถ้า Firestore error ตอนอ่าน/เขียน history → fallback เป็น "ไม่มีความจำ" (เหมือนพฤติกรรมปัจจุบัน) ไม่ใช่ error ทั้งข้อความ

### ✅ ตัดสินใจแล้ว
เก็บสูงสุด **10 คู่** (20 ข้อความ) ตามที่เสนอ ใช้ history ร่วมกันระหว่างโหมด task/chat

### Effort โดยประมาณ
กลาง — ต้องแก้ `gemini_service.py` ให้รับ/ส่ง history, เพิ่ม `history_service.py` ใหม่, แก้ webhook_handler ให้โหลด/บันทึก history รอบ message

## ฟีเจอร์ที่ 2: สรุปงานประจำวันอัตโนมัติ (Daily Briefing)

### ปัญหา
ระบบเป็น "reactive" ล้วน ผู้ใช้ต้องถามเองทุกครั้ง ไม่มีการแจ้งเตือนเชิงรุกว่าวันนี้มีอะไรครบกำหนด/เลยกำหนดบ้าง

### เป้าหมาย
ทุกเช้า (เวลาที่กำหนด เช่น 08:00 ตามเวลาไทย) บอทส่งสรุปงานที่ครบกำหนดวันนี้ + งานที่เลยกำหนดแล้ว ให้ผู้ใช้แต่ละคนแบบ push message โดยไม่ต้องถาม

### จุดที่ต้องตัดสินใจก่อน (สำคัญมาก — บล็อกการออกแบบที่เหลือ)
ตอนนี้ระบบรู้จัก dh-task identity ("assignee") ของ**แอดมินคนเดียว**เท่านั้น (ผ่าน `SELF_EMAIL` ใน config) ผู้ใช้ LINE คนอื่นที่ผ่านการอนุมัติแล้ว **ยังไม่มีการ map ว่าเขาคือ user ไหนใน dh-task** ดังนั้นก่อนทำสรุปงานรายบุคคลให้ทุกคนได้ ต้องตอบคำถามนี้ก่อน:

- **ตัวเลือก A**: ทำสรุปงานให้เฉพาะแอดมิน (คุณ) ก่อน — ง่ายสุด ทำได้ทันที ไม่ต้องแก้ระบบ registration
- **ตัวเลือก B**: ขยายหน้า LIFF verification ให้ผู้ใช้ใหม่กรอก/เลือกอีเมล dh-task ของตัวเองตอนสมัคร แล้วเก็บ mapping ไว้ใน `bot_users/{user_id}.dhtask_email` — ทำให้ทุกคนได้สรุปงานของตัวเองจริงๆ แต่ใช้เวลาเพิ่ม

### ✅ ตัดสินใจแล้ว: เลือกตัวเลือก A (สรุปงานให้เฉพาะแอดมินก่อน)

### Data model
เพิ่ม field ใน `bot_users/{user_id}`:
```
daily_briefing_enabled: true/false   (default: true สำหรับผู้ใช้ approved)
last_briefing_date: "2026-07-14"     (กันส่งซ้ำในวันเดียวกัน)
```

### Flow
1. External cron (ตัวเดียวกับที่ตั้งไว้แล้วสำหรับ reminders) ยิง `/cron/daily-briefing?token=...` ทุกครั้งที่ตรงเงื่อนไขเวลา (เช่น cron-job.org ตั้ง job แยกให้ยิงตอน 08:00 ทุกวันตามเวลาไทยไปเลย ไม่ต้องเช็คเวลาในโค้ด)
2. Endpoint loop ผู้ใช้ที่ `status == approved` และ `daily_briefing_enabled == true` และ `last_briefing_date != today`
3. เรียก `k-list --due-filter Today` และ `k-list --due-filter Overdue` (กรอง assignee ตามตัวเลือก A/B ด้านบน)
4. ส่งเป็น Flex Message สรุป + อัปเดต `last_briefing_date`
5. ถ้า user คนใดคนหนึ่งพังระหว่างทาง (Firestore/dh-task error) → log แล้วข้ามไปคนถัดไป ไม่ทำให้ทั้ง batch ล้มเหลว

### คำสั่งเปิด/ปิด
พิมพ์ "ปิดสรุปประจำวัน" / "เปิดสรุปประจำวัน" → toggle `daily_briefing_enabled`

### Effort โดยประมาณ
กลาง-สูง — ขึ้นกับว่าเลือก A หรือ B; A ทำได้เร็ว (endpoint ใหม่ + Flex message ใหม่), B ต้องแก้ LIFF form ด้วย

## ฟีเจอร์ที่ 3: ยืนยันก่อนลบ/แก้ไขข้อมูลจริง (Confirm Before Destructive Actions)

### ปัญหา
`run_klive_command` เรียก `k-delete` ได้ทันทีจาก Gemini โดยไม่มีมนุษย์ยืนยัน พิมพ์ผิด/AI เข้าใจผิด → ข้อมูลหายจริงในระบบ dh-task ทันที ไม่สามารถ undo ได้

### เป้าหมาย
Action ที่ **ลบข้อมูลถาวร** ต้องมีปุ่มยืนยัน (Approve/Cancel) ก่อนสั่งจริง เหมือนกลไก approve/deny ที่มีอยู่แล้วสำหรับสมัครสมาชิก

### ขอบเขต — อะไรต้องยืนยัน อะไรไม่ต้อง (✅ ตัดสินใจแล้ว)
| Action | ต้องยืนยันไหม | เหตุผล |
|---|---|---|
| `k-delete` (ลบงาน) | ✅ ต้อง | ลบถาวร กู้คืนไม่ได้ |
| `k-milestone-delete` | ✅ ต้อง | ลบถาวร กู้คืนไม่ได้ |
| `k-update` | ✅ ต้อง | อาจเผลอเปลี่ยนกำหนดส่ง/สถานะผิดโดยไม่ตั้งใจ |
| `k-milestone-update` | ✅ ต้อง | เหตุผลเดียวกับ k-update |
| `k-create` | ❌ ไม่ต้อง | สร้างใหม่ ไม่กระทบของเดิม |

### Flow
1. Gemini forced-tool-call resolve ออกมาเป็น `k-delete` / `k-milestone-delete` / `k-update` / `k-milestone-update`
2. **ไม่เรียกจริงทันที** — เรียก `k-get`/`k-milestone-get` ก่อนเพื่อดึงข้อมูลปัจจุบันมาแสดง (กันกรณีชื่อซ้ำ/AI เข้าใจผิด task, และสำหรับ update ให้โชว์ค่าเดิม vs ค่าใหม่ที่จะเปลี่ยน)
3. เก็บ pending action ไว้ใน Firestore (`pending_actions/{action_id}`: user_id, command_args, created_at, หมดอายุใน 5 นาที)
4. ส่งข้อความยืนยัน พร้อมปุ่ม ✅ ยืนยัน / ❌ ยกเลิก (postback data=`confirm_action&id=...` / `cancel_action&id=...`)
   - ลบ: "ต้องการลบงาน '[ชื่อจริง]' ใช่ไหมครับ?"
   - แก้ไข: "ต้องการเปลี่ยน [field] ของงาน '[ชื่อจริง]' จาก '[ค่าเดิม]' เป็น '[ค่าใหม่]' ใช่ไหมครับ?"
5. ผู้ใช้กด → เช็คว่า postback มาจาก user_id เดียวกับที่ขอ (กันคนอื่นกดแทน) → ถ้ายืนยัน เรียก klive command จริง, ถ้ายกเลิกหรือหมดอายุ → ไม่ทำอะไร

### Effort โดยประมาณ
กลาง — เพิ่ม Firestore-backed pending-action store (pattern คล้าย notes/reminders ที่มีอยู่แล้ว), แก้ `gemini_service.py` ให้ intercept ก่อนเรียกจริงสำหรับ 4 subcommand นี้ (delete/update ทั้งงานและ milestone), เพิ่ม postback branch ใหม่ใน `webhook_handler.py`

## จำลอง User Journey แต่ละฟีเจอร์

### ฟีเจอร์ 1: ความจำบทสนทนา

**Journey A — ถามต่อเนื่องแบบมีบริบท (กรณีปกติ)**
```
ผู้ใช้:  งานของฉันมีอะไรบ้าง
บอท:   [การ์ด Flex] คุณมี 3 งานที่ยังไม่เสร็จครับ
ผู้ใช้:  งานแรกกำหนดส่งเมื่อไหร่
บอท:   งาน "ออกแบบหน้า Login" กำหนดส่ง 20 ก.ค. 2569 ครับ
       ← จำได้ว่า "งานแรก" หมายถึงอันไหนจากที่คุยไปก่อนหน้า
```
เทียบกับพฤติกรรมปัจจุบัน (ไม่มีความจำ): บอทจะถามกลับว่า "หมายถึงงานไหนครับ ช่วยระบุชื่อ" ทุกครั้ง

**Journey B — ความจำหมดอายุอัตโนมัติ (3 ชม.)**
```
09:00  ผู้ใช้: งานของฉันมีอะไรบ้าง
       บอท:   [แสดงรายการ]
13:30  ผู้ใช้: อันนั้นกำหนดส่งวันไหนนะ
       บอท:   ขอโทษครับ ไม่แน่ใจว่าหมายถึงงานไหน ช่วยระบุชื่องานอีกครั้งได้ไหมครับ
       ← ผ่านมาเกิน 3 ชม. ความจำถูกเคลียร์อัตโนมัติ กันเอาบริบทเก่าคนละเรื่องมาต่อผิด
```

**Journey C — เคลียร์เอง**
```
ผู้ใช้:  เริ่มคุยใหม่
บอท:   เคลียร์ประวัติสนทนาแล้วครับ เริ่มกันใหม่ได้เลย
```

**Journey D — Firestore ล่ม (fail-open)**
```
ผู้ใช้:  งานนั้นกำหนดส่งเมื่อไหร่
[ระบบ]: ดึงประวัติสนทนาจาก Firestore ไม่ได้ (error)
บอท:   ขอโทษครับ ไม่แน่ใจว่าหมายถึงงานไหน ช่วยระบุชื่องานได้ไหมครับ
       ← ตอบกลับปกติแบบไม่มีความจำ ไม่ error ทั้งข้อความ
```

### ฟีเจอร์ 2: สรุปงานประจำวันอัตโนมัติ

**Journey A — เช้าวันธรรมดา มีงานครบกำหนด + เลยกำหนด**
```
08:00  [Push อัตโนมัติ ไม่ต้องถาม]
บอท:   🌞 สรุปงานประจำวันที่ 15 ก.ค. 2569
       📌 ครบกำหนดวันนี้ (2)
       1. ทำ Rich Menu ให้เสร็จ
       2. Review PR ทีม Dev
       ⚠️ เลยกำหนดแล้ว (1)
       1. อัปเดตเอกสาร API (เลยมา 3 วัน)
```

**Journey B — วันที่ไม่มีงานครบกำหนดเลย**
```
08:00  บอท: 🌞 วันนี้ไม่มีงานครบกำหนดครับ เก็บแรงไว้ลุยงานอื่นได้เลย 🎉
```
(จุดตัดสินใจ: จะส่งข้อความให้กำลังใจแบบนี้ทุกวัน หรือไม่ส่งอะไรเลยถ้าไม่มีงาน — เลือกได้)

**Journey C — ผู้ใช้ปิดการแจ้งเตือน**
